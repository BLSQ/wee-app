Part 1 · Why

TDD before agents

Benefits

  • Tests describe behaviour
  • Pressure towards testable design
  • A safety net for later changes

Costs

  • More to write up front
  • Tests rewritten when the design moves
  • Often dropped near a deadline
Ask the room: who does strict TDD today? Who tried and stopped, and why?

Part 1 · Why

What changes with coding agents

Writing tests costs less

The agent writes and rewrites them.

Reviewing costs more

Hundreds of lines arrive in minutes.

Tests give a feedback loop

The agent can check its own work.

Producing code is less of a bottleneck; knowing whether it does what we wanted becomes a bigger one. Tests and specs both help with that. With tests to run, the agent can also work alone for longer.

Part 1 · Why

Red, green, refactor

RedOne failing test
GreenJust enough code to pass
RefactorClean up, tests stay green
The failing run shows that the test really checks something. Agents tend to skip it; the TDD skill asks for it explicitly. In the terminal this step goes by quickly and is easy to miss: do not ask participants to spot it. Someone curious can ask the agent to stop after the first failing test.

Part 1 · Why

Spec-driven development

  • Agree on what and why before the code
  • A short spec is quicker to review than a diff
  • The spec stays in the repo after the chat session ends

Today: one page

  • Purpose
  • Approaches considered, and why this one
  • Shape of the query or component
  • Acceptance criteria
  • Out of scope
A misunderstanding is usually cheaper to fix in the spec than in the plan, and cheaper in the plan than in the code. The spec can also be read later by another agent or a colleague.

Part 1 · Why

Architecture Decision Records (ADRs)

An ADR is a short file in the repo that records one technical decision.

  • Context: the situation
  • Decision: what was chosen, what was rejected
  • Consequences: what gets easier or harder
0007. GeoJSON in jsonb instead of PostGIS Status: Accepted Context The dashboard draws districts on a map. IASO stores geometry with PostGIS. Decision Simplified GeoJSON in a jsonb column. No PostGIS. Consequences No extension needed. No spatial queries in SQL. Revisit if a ticket needs one.

More adr.github.ioOriginal post Documenting Architecture Decisions (Nygard, 2011)

Some participants will not know the concept: read the example aloud. It is a condensed version of docs/adr/0007. Useful later, when someone wonders why something was done this way. The usual practice is to supersede an ADR with a new one rather than rewrite it. Format from Michael Nygard (2011).

Why ADRs work well with agents

  • An agent starts each session without history
  • It reads docs/adr/ before brainstorming
  • After a plan, it proposes ADRs; you decide

Three places where code runs: the browser, the Node.js server, and the database. The page asks for data; tRPC carries the call to the server, where a procedure checks the input and calls a query; the query sends SQL to Postgres. The rows come back the same way, and the page hands them to the component. If there is time, open src/features/device-syncs/ and show the files: they are short. A new feature usually means the same files in a new folder, plus one line in each registry. ui/ only imports types from the server side.

Part 2 · Wee-App

What gets a test

HowPattern to copy
QueryReal SQL on a Postgres that runs inside the test (PGlite); each test inserts its rowsqueries.test.ts
ComponentRendered with props in a simulated browser (jsdom); find by role and text, clickSyncTable.test.tsx
Page, procedureNo test: the type-check, then try the feature
Whole appThe preview of the pull request

No test replaces the database or a component with a fake (a mock): a test that passes means the real code ran. pnpm test runs everything in a few seconds, with nothing to start first.

For Django people: a query test is like a TestCase, except that the test database lives inside the test process and starts empty in every file. The database is not mocked because the logic of a query is its SQL, and a mock would not run it. A page only fetches and passes data, so the type-check covers it: tRPC types run from the query to the page. A procedure with logic of its own, such as sign-in, is tested by calling it directly on the test database. jsdom computes no layout and no colours: how a page looks is checked on the preview.

Agent instructions: CLAUDE.md

Rules

  • Everything in English
  • Skills are mandatory
  • Read the ADRs first; propose ADRs after
  • Worktree, then pull request; never main
  • Test the queries and the components
  • Write for Python developers: explain the jargon
  • No linter, e2e, auth or CI: they are issues

Pace, for today

  • Questions in batches of three, two batches at most
  • Then two or three approaches
  • One-page spec, one-page plan
  • No sub-agents, one round of review
The file is about sixty lines, short on purpose; details live in skills and ADRs. The pace rules shorten each Superpowers step and skip none. Without them the agent asks its questions one at a time, with no limit, and writes longer specs and plans. .claude/settings.json makes you, not Claude, the author of your commits.

1 · Root causeRead, reproduce. No fix yet

Fix failed?Under 3: back to 1

In this repo: the deployed app fails with relation "device_sync" does not exist

1 · Root cause
The deployment is fine. The migration command had run against a developer's local database
2 · Pattern
Locally the tables exist; in production they do not
3 · Hypothesis
Production was never migrated
4 · Fix
Migrate during the deploy build; a failing migration now fails the build
redeployrun db:migrate againneither touches the production database
From ADR 0012 and its spec. The error pointed at the deployment, and the deployment was fine: the migration command had run against the developer's local database, because that is where .env pointed. Redeploying, or running the migration again, would have changed nothing in production. The fix is at the cause: Vercel's build command is now pnpm db:migrate && pnpm build. Django people know this one: it is forgetting to run migrate on the server. The skill also sets a threshold: after three failed fixes it stops trying and questions the architecture.

Round table · Inside Superpowers

Verification before completion

Before any "done", the skill asks for the output of a check run just now. The check has to match the claim.

# the claim: "the syncs page works". The check: the tests$ pnpm test ✓ all tests pass
# what a user saw on /syncsa spinner that never ends ReferenceError: Can't find variable: Buffer

The tests run in Node and never load the page. For "the page works", the matching check is to open the page.

From ADR 0010. A browser file imported the feature registry, which also exported the server router, so the Postgres driver ended up in the code sent to the browser. The tests never build that code, so they stayed green while the page was broken. This is why the Verify step of the workflow ends with "try the feature", and why a deployment change is verified on the preview URL. Since then a test, AppShell.test.ts, fails if the application shell can reach the database driver. The terminal output on the slide is simplified.
