Part 1 · Why

TDD before agents: benefits and costs

Benefits

  • Tests that describe behaviour, not implementation
  • Design pressure: hard to test means badly shaped
  • A safety net for later changes

Costs, in practice

  • More to write before anything shows on screen
  • Tests to rewrite when the design changes
  • Often dropped when a deadline gets close
  • Many teams end up writing tests afterwards
Ask the room: who does strict TDD today? Who tried and stopped, and why? Collect two or three answers.

Part 1 · Why

What changes with coding agents

Writing tests costs less

The agent writes the tests, and rewrites them when the design changes. Most of the cost listed on the previous slide goes away.

Reviewing takes more effort

An agent can produce several hundred lines in a few minutes. Reading all of it carefully is hard, so automated checks become more useful.

Tests give the agent a feedback loop

With tests to run, the agent can work on its own for longer and correct itself, and "done" can be checked.

With an agent, producing code is less of a bottleneck; knowing whether the code does what we wanted becomes a bigger one. Tests and specs both help with that.

Part 1 · Why

Red, green, refactor

RedWrite one test for one behaviour. Run it. Watch it fail, for the right reason.
GreenWrite just enough code to make it pass.
RefactorClean up while the tests stay green.

Seeing the test fail first confirms that it actually tests something. Agents tend to skip this step; the TDD skill asks for it explicitly.

During the build rounds, this is the thing to watch in the terminal: does the agent run the test and show the failure before writing the implementation?

Part 1 · Why

Spec-driven development

  • Agree on what and why before any code exists
  • A short spec is quicker to review than a large diff
  • A chat session gets compacted or closed; a file in the repo stays
  • The spec can be read later by another agent, or by a colleague

Today's spec is half a page

Purpose. Shape of the query or the component. Acceptance criteria. Out of scope.

The "out of scope" section is often the most useful one.

A misunderstanding is usually cheaper to fix in the spec than in the plan, and cheaper in the plan than in the code.

Part 1 · Why

Superpowers: a method and some discipline

Agents know TDD, but they tend to skip steps when a task looks simple or when they are stuck.

The skills try to prevent that with explicit gates, a few "iron laws", and lists of common excuses with an answer to each.

test-driven-developmentNo production code without a failing test first
systematic-debuggingNo fixes without root cause investigation first
verification-before-completionNo completion claims without fresh verification evidence
We come back to these at the checkpoint, with examples from building this very repository.

Part 1 · Why

When is it worth it?

Throwaway prototype

Usually not. The goal is to explore quickly, and the process slows that down.

A task of a day or two

Debatable. Recent models often manage with a direct prompt, and the process may cost more time than it saves.

Several days to weeks

Often yes. The work no longer fits in one session or one reviewable diff; the spec and the plan help keep track.

A product that lives

Yes. Specs and ADRs also keep a record of why things were built this way.

Note: today's issues are small (S and M), and the repo has a "pace budget" so that the whole workflow fits in three hours. Today is more about discovering the workflow than measuring a time gain.

Somebody may say "I would have done this faster with a plain prompt". That is probably true at this size. Invite them to imagine the same workflow on a three-week IASO feature. These thresholds are an opinion, open to discussion.

Part 1 · Why

Architecture Decision Records (ADRs)

An ADR is a short document, usually one page, that records one technical decision and the reasons behind it. ADRs are numbered and kept in the repository, next to the code.

  • Context: the situation and the constraints
  • Decision: what was chosen, and what was considered and rejected
  • Consequences: what this makes easier or harder, and when to revisit

Useful later, when someone wonders why something was done this way. When a decision changes, the usual practice is to write a new ADR that supersedes the old one.

0007. GeoJSON in jsonb instead of PostGIS Status: Accepted Context The dashboard draws districts on a MapLibre map. IASO stores geometry with PostGIS. Decision Simplified GeoJSON in a jsonb column. No PostGIS extension. Consequences The database needs no extension. There are no spatial queries in SQL. Revisit if a ticket needs one.
Some participants will not know the concept: take the time to read the example aloud. It is a condensed version of docs/adr/0007 in the repo. The format comes from Michael Nygard (2011).

Part 1 · Why

Why ADRs work well with agents

  • An agent starts each session without history, so it may propose again an option that was already rejected
  • ADRs are short, so the agent can read all of docs/adr/ before brainstorming
  • After a plan is implemented, the agent proposes ADR additions, and you decide
  • Writing them costs little: the agent drafts, you review

Part 2 · Wee-App

The use case: IASO device synchronisations

IASO mobile devices synchronise their data. When a device stops syncing, data stops arriving from that area, and it can take a while before someone notices. Who has not synced recently, and where?

Wee-App is a small dashboard over those syncs. Today it has one page with one table. The rest is in the backlog.

Real org-unit pyramid from an IASO dump, synthetic syncs, no personal data. The seed is deterministic: everybody has the same rows, and tests assert against them.

A sync row: device, user, date, number of submissions, org units and entities synced. Devices have profiles in the seed: healthy, dropped, silent, mixed. That is what makes "who stopped syncing" an interesting question.

Part 3 · How we work

Review by another pair

  • As soon as the spec is committed: push, open a draft pull request, assign the next pair as reviewers
  • They review your spec while your agent implements; feedback at that stage is easier to take into account
  • When the PR is ready, they review the code and the preview URL
  • Review ring: pair 1 → pair 2 → … → pair 1

What to look at

  • Does the spec answer the issue, and say what is out of scope?
  • Do the tests describe behaviour a user would recognise?
  • Does the preview do what the spec says?
  • Is there a decision here that deserves an ADR?
This helps with the waiting time: while one pair waits for its agent, it can review another pair.

Part 3 · How we work

Merging, and merge conflicts

  • Once the other pair has approved, you merge your own pull request
  • Conflicts will probably happen: several pairs add a line to router.ts and nav.ts, and some touch package.json or add a migration
  • The simplest way is to ask your agent, in the same session and worktree

Afterwards, check

  • Both features are still registered, yours and theirs
  • pnpm-lock.yaml was regenerated with pnpm install, not merged by hand
  • Two migrations with the same number: yours takes the next one
  • Tests and type-check pass, and the preview still works
> Merge origin/main into this branch and resolve the conflicts. Keep the features from both sides. Run the tests and the type-check, then push.
Merging main into the branch, rather than rebasing, avoids force-pushes on a pull request that is under review. The first pairs to merge will have no conflict; the later ones will, so mention it again around 2:15.

Systematic debugging: four phases and a limit

1 · Root causeRead the error, reproduce, check recent changes. No fix yet.
→
2 · PatternFind something similar that works; list the differences.
→
3 · HypothesisOne at a time, tested with the smallest possible change.
→
4 · FixA failing test first, then one fix, then verify.

Checkpoint · Inside Superpowers

Verification before completion

Before saying "done", the agent has to run the check and show its output. An example from building this repo, with the first deployment adapter:

# what was checked: a smoke test, run inside the repo$ node smoke-test.mjs ✓ GET /syncs → 200
# what mattered: the preview deployment$ curl -I https://…vercel.app/syncs HTTP/2 500 FUNCTION_INVOCATION_FAILED

The local test passed because node_modules happened to be there; on Vercel it was not. Since then, "verified" for a deployment change means the HTTP status of the preview.

Link back to the red step: it helps to have seen a check fail at least once, in conditions close to the real ones. The commands on the slide are simplified.
